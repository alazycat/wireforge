Issue #6 — IPv6 解析与构造（含扩展头链） — 2026-06-13

Design Decisions

Decision Zero-copy payload() not bounded by payload_length()

Ambiguity: The spec does not specify whether payload() should truncate to the declared payload_length field or return all bytes after the last parsed header.

Choice: Returns all remaining bytes after peeling extension headers, without truncating to payload_length. Matches the IPv4 parser's behavior in this crate.

Rationale: Consistent with the zero-copy design philosophy across the crate. If the underlying buffer has trailing data (common in captures), callers can truncate themselves. The extra bytes are harmless for upper-layer parsing since TCP/UDP parsers also read their own length fields.

Decision Shared extension_header_len() helper for all parsing paths

Ambiguity: Extension header length computation is needed in three places: payload(), final_protocol(), and the iterator.

Choice: Extracted into a single extension_header_len(proto, data) -> usize function used by all three.

Rationale: Avoids duplicate match arms. If a new extension header type is added (e.g., Mobility), only one location needs updating.

Decision Builder silently drops invalid extension header data

Ambiguity: How should add_extension_header() handle invalid data (too short, Fragment header not exactly 8 bytes)?

Choice: Silently return self without adding the header. No Result return type — the method stays chainable with the fluent builder pattern.

Rationale: Avoids breaking the builder chain with error handling at every step. Callers get a valid (if possibly simplified) packet on build(). Major errors (e.g., payload too large) still use BuildError.

Deviations

Deviation Builder truncates extension headers at MAX_EXTENSION_DEPTH (8)

Spec said: Add extension headers via add_extension_header() — no limit specified.

Implemented: build() silently truncates the extension header list to 8 entries, matching the parser's iteration limit.

Why: Consistency between builder and parser. A 12-header packet built by this library would be unparseable by the same library's parser otherwise. RFC 8200 recommends against deep chains.

Tradeoffs

Tradeoff Raw extension header bytes vs typed extension header builder

Alternatives: (A) Accept raw bytes with next_header field, rewrite chain in build() — chosen approach. (B) Accept only the body bytes, auto-prepend next_header. (C) Typed enum variants for each extension header type.

Why A: Most transparent about wire format. Users construct extension headers exactly as they appear on the wire. The next_header chain rewiring in build() is an explicit, documented transformation. Option C would be ideal but requires more API surface for relatively uncommon use cases.

Open Questions

Question Should additional IPv6 extension header types be recognized?

Currently recognized: HopByHop (0), Routing (43), Fragment (44), Destination (60). Not recognized: ESP (50), AH (51), Mobility (135), No Next Header (59). These are treated as non-extension protocols, ending the chain.

Question Should the builder validate minimum data lengths per extension header type?

Currently only Fragment (exactly 8 bytes) and a general minimum of 2 bytes are enforced. HopByHop, Destination, and Routing headers have no per-type minimum validation beyond that.
